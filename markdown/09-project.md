# 项目关联：给期末系统增加可靠的任务反馈

## 从UI原型走向异步业务

以案例库或FDE工作台为背景，把一次需要等待的操作设计成可观察任务，例如“校验导入记录”或“生成模拟诊断摘要”。页面先创建任务，随后展示进度与结果；先使用模拟执行，不要求接入真实模型或完整平台日志。

不要把模拟百分比描述为真实模型完成度。若无法知道剩余工作量，可显示阶段、已接收消息数和经过时间，而不是编造精确的80%。

## 最小业务切片

| 层 | 需要完成 | 可观察证据 |
|---|---|---|
| UI | 创建、连接提示、进度、失败、取消 | 连接断开与任务失败可区分 |
| API | 创建、快照、订阅、取消契约 | 重连不重复创建任务 |
| 状态 | 服务端任务状态与递增事件位置 | 取消幂等、终态不倒退 |
| 数据 | 当前快照与明确的历史保留规则 | 历史不足时说明缺口 |
| 权限 | 接入已有登录与对象授权 | 他人不可订阅或取消私有任务 |

先复现[labs/realtime-basics](labs/realtime-basics/README.md)，再把机制迁入自己的项目。独立实验没有账号系统，不能直接以其本机开放接口替换第八讲的安全设计。

## 对照已有course-lab

course-lab的server/app.mjs已有受保护的runs/:id/events，客户端RunView展示trace。它推送审批与运行轨迹，不是真实模型token流；其done还可能表示30秒订阅期限结束，不能直接当作任务完成。

先解释现有实现，再选择一个增量：同步snapshot中的业务状态；在不重新POST的前提下恢复订阅；记录断开与结束时间；为历史和界面日志设置容量。取消任务是另一个业务契约，不能把管理员拒绝审批与一般执行取消混为一谈。

## 结果检查

正常与失败路径都要可演示。断开订阅不应意外结束任务；重新订阅不产生新的业务任务；明确取消后以服务端返回状态为准；已有日志不会重复追加。事件与用户输入通过文本方式呈现。

## 按需要拓展

持久化任务与事件，讨论进程重启后的恢复；为多个观察页面同步同一任务；设计CANCELLING与外部执行者确认；比较轮询方案在延迟与请求数上的代价。WebSocket、消息队列和多实例广播按真实需求选择，不作为本讲最低完成条件。
