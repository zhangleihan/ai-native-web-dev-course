# 恢复、取消与部署：连接之外还需要什么

## 1. 先定义任务状态转换

```text
创建 → RUNNING → COMPLETED
           ├──→ FAILED
           └──→ CANCELLED
```

本实验的三个终态不会再变回RUNNING。重复取消返回现有终态，不重复写入取消事件。任务已经完成时再点取消，返回COMPLETED，而不是把既成结果改成已取消。

真正耗时的外部操作未必能瞬间停止。生产系统可先进入CANCELLING，向工作进程发送取消信号，待执行者确认后再写CANCELLED；已发生的外部副作用还需要独立处理。本实验只有内存定时器，可以同步清理，不能据此推断模型调用或远程工具也能立即撤销。

## 2. 断开连接只清理订阅资源

| 资源 | 生命周期 | 结束条件 |
|---|---|---|
| 任务推进定时器 | 属于任务 | 完成、取消、失败或服务退出 |
| 订阅发送定时器 | 属于某个HTTP响应 | 客户端关闭、终态结束或服务退出 |
| 事件历史 | 属于任务 | 超出保留上限淘汰；重启清空 |
| React EventSource | 属于页面上的当前订阅 | 切换任务、主动停止、终态或组件卸载 |

服务端监听响应的close，幂等清理该连接的发送定时器与drain监听器，并减少订阅计数。页面close不会调用业务cancel。一个任务被两个页面订阅时，关闭其中一个页面也不应停止另一个页面的业务。

## 3. 从已知位置补发

假设任务产生了编号1–8的变化，页面处理到#2时断开。

```text
客户端：已处理#1、#2 → 断开
服务端：继续保存#3、#4……
客户端：重新GET events，位置=2
服务端：按顺序发送编号>2的已保留事件，再发送后续事件
```

Last-Event-ID只是位置声明。服务器仍须识别任务、检查权限、验证位置，并读取该任务历史。本例拒绝负数、非整数及超过当前seq的位置，避免客户端跳过尚不存在的变化。

事件可能重发。客户端按“任务id+事件编号”识别已处理消息；若事件会触发业务副作用，还需要服务器端的幂等业务设计，不能只依靠页面去重。

## 4. 历史过期时承认缺口

本例只保存最近6条历史。任务已完成到#8时，服务器只剩#3–#8；若客户端请求从0恢复，不能声称给出全部过程。

服务端发送自定义reset：data携带当前完整快照，id设为当前seq。客户端将该快照作为新基线，清理不完整的日志列表，并明确提示较早日志不可回放。随后收到done时关闭。

快照可以恢复“任务现在已完成到哪一步”，不能恢复已经丢失的中间文字。若业务要求审计全程，应持久化事件或其他审计记录，不能只增大浏览器数组。

## 5. 避免快照与订阅之间漏事件

“先GET快照，再只订阅未来”存在窗口：读完快照后、订阅建立前产生的变化可能丢失。一种方案是让快照带seq，再从这个位置补发；另一种是由服务器在订阅响应里协调历史与当前状态。

本实验订阅先按游标补发，再同步snapshot并继续观察。状态读取、历史复制和写入都在单进程内同步执行，中间没有跨存储await，避免在这段代码中插入另一轮定时器更新。若扩展为多进程与数据库，不能沿用这个局部保证，应设计一致的事件提交、顺序与恢复协议。

完整客户端还会比较快照seq，避免手动GET的较新状态被随后到达的旧事件覆盖。位置、状态和日志分别维护，不能用一项变量替代三者。

## 6. 心跳用于连接维护

服务器可在没有业务事件时发送注释：

```text
: heartbeat

```

它不会触发progress，也不能让任务进度增加。周期应结合网关的空闲超时和业务流量选择，没有适合所有部署的固定值。本例设置约5秒，但正常任务约4.8秒结束，通常不容易在浏览器观察到心跳；可阅读源码或在独立样本中增加任务间隔观察。

收到心跳只能说明该连接仍在传输，不能证明模型仍在有效推理；业务健康与连接存活需要分别判断。

## 7. 背压与容量限制

当生产速度高于接收速度时，未发送数据可能在内存中累积。背压是下游处理不过来时，要求上游减速或暂停的机制。

Node响应write返回false并不表示该帧发送失败或需要重发，它表示缓冲压力已达到阈值。应暂停继续写，等待drain再推进；[Node HTTP文档](https://nodejs.org/docs/latest-v20.x/api/http.html#responsewritechunk-encoding-callback)用于核查这个含义。

本例记录已交给write的事件位置，阻塞期间暂停该订阅的发送，drain后继续。历史若在此期间被淘汰，采用reset恢复当前快照。它没有为每个慢客户端保存无限消息队列，也没有提供完整生产流控；强制制造背压、海量客户端与压测不在当前自动测试范围内。

## 8. 代理为什么可能让“实时”变成“一次出现”

应用持续写出数据，不代表代理立即转发。排查时分别比较本机直连和经代理访问的到达时间。Nginx可按路由关闭响应缓冲，示意配置如下；需要放在实际server配置中，不是本例启动必需项。

```nginx
location /api/tasks/ {
    proxy_pass http://127.0.0.1:3009;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_read_timeout 60s;
}
```

该location也会代理任务的快照和取消接口。60秒是示例读取空闲超时，应与心跳等配置一起验证；不是任务时长限制。应用的X-Accel-Buffering响应头可影响相关代理，但也可能被配置忽略。[Nginx代理模块](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_buffering)

还需确认网关是否支持长响应、是否有最大连接时长、内容压缩是否引入额外缓冲。不要在本机直连通过后宣称云部署也已经验证。

## 9. fetch流是进阶方案

需要POST请求体或自定义头时，可以读取fetch的Response.body。流程是：检查HTTP状态与内容类型→取得reader→用TextDecoder增量解码→保存跨块残留→按SSE行与帧规则处理→在结束和取消时清理reader。

```javascript
// 仅说明字节解码；不是完整SSE解析器。
const reader = response.body.getReader();
const decoder = new TextDecoder();
let pending = '';
while (true) {
  const {done, value} = await reader.read();
  if (done) break;
  pending += decoder.decode(value, {stream: true});
  // 从pending取完整事件；将不完整的尾部留到下一次。
}
pending += decoder.decode();
```

完整实现还要处理换行规则、data多行、id/retry、异常、响应体为空和AbortController。配套Node验证客户端只解析本实验生成的LF与JSON，不是通用浏览器EventSource替代品。[MDN可读流教程](https://developer.mozilla.org/en-US/docs/Web/API/Streams_API/Using_readable_streams)说明流读取的基础接口。

取消读取或AbortController.abort只终止当前客户端传输，不能代替业务取消接口。工具已产生的外部副作用也不会因传输中断自动回滚。

## 10. 与现有course-lab的差异

| 项目 | 本讲realtime-basics | 现有course-lab |
|---|---|---|
| 业务 | 独立6步模拟任务 | 建议、工具提案与审批轨迹 |
| 认证 | 本机无账号实验 | 服务端会话、CSRF与资源授权 |
| 恢复历史 | 有界历史、after/Last-Event-ID、reset | run.trace与Last-Event-ID |
| 主动取消 | 单独cancel接口 | 原有decision拒绝，不是通用任务cancel |
| done含义 | 本例仅终态发送 | 终态或30秒订阅期限到达 |
| 客户端断线 | 允许原生重连并提供手动恢复 | 当前实现关闭连接并提示刷新 |

因此不能把course-lab收到done解读为任务必然完成，也不能把其已有接口称为完整后台队列或模型token流。本讲新增实验补充学习所需机制，保留原有审批业务。

<details><summary>write返回false后，应该把刚才的帧再发一次吗？</summary><p>不应直接重发。该数据已经交给写缓冲，应暂停后续写入并等待drain，避免重复。</p></details>

<details><summary>实验中的reset恢复了什么？</summary><p>当前任务快照与后续消费基线；已经淘汰的中间日志没有恢复。</p></details>
