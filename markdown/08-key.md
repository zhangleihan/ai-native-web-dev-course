# 身份认证与Web安全：建立可验证的信任边界

## 学习目标与课前准备

第五至第七讲让数据通过API进入数据库。本讲回答接下来的问题：服务器怎样知道请求者是谁？登录后能否修改所有记录？浏览器自动携带的Cookie怎样受到保护？

学完后，应能区分认证、授权与会话，解释Cookie、服务端会话和JWT的关系，为案例资源设计权限表，追踪登录与退出流程，并通过失败请求证明越权或伪造操作没有改变数据。

先修为HTTP、API校验、数据归属与前后端请求；实践使用已有course-lab中的alice、bob、admin隔离练习账号。本讲沿用服务端会话主线，JWT/OAuth/OIDC作为概念比较，不要求同时实现多套登录。

## 1. 从一次越权请求理解风险

案例A由alice维护，案例B由bob维护。如果前端只把bob案例上的编辑按钮隐藏，alice仍可能自己构造HTTP请求修改B。服务器必须检查请求身份和资源归属，而不能推断“能发出请求的人一定有权限”。

```text
客户端提交请求
  → 来源与CSRF检查
  → 从服务端会话确认当前用户
  → 根据资源与操作检查权限
  → 校验允许写入的字段
  → 执行受约束的数据操作
  → 返回结果并保留必要证据
```

顺序会影响错误表现。现有实验先做CSRF检查，再做登录检查，因此完全缺少CSRF的匿名写请求会先得到403；携带有效匿名CSRF但尚未登录，才会得到401。不能用“任意未登录请求都应返回401”判断实现。

## 2. 四个经常混淆的概念

| 概念 | 回答的问题 | 本课例子 |
|---|---|---|
| 身份认证 Authentication | 请求者是谁？ | 用练习口令登录alice |
| 会话管理 Session Management | 后续请求怎样延续这次身份？ | Cookie携带会话标识，服务端加载记录 |
| 授权 Authorization | 此人能对这条资源做什么？ | alice只能修改自己的案例，admin可跨用户修改 |
| 追踪与审计 | 发生了什么、为何允许或拒绝？ | 记录操作结果与对象，验证失败无副作用 |

认证成功不能替代资源授权。知道账号为alice，还必须判断目标案例是否归alice，或者服务端是否确认该账号具有所需管理权限。[OWASP授权原则](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

浏览器上的用户对象用于展示，不是权限凭证。服务器应从经过验证的会话加载身份；请求体里的userId、ownerId、role都属于客户端声明，不能直接作为可信身份。

## 3. 列出资产、入口与信任边界

先找出要保护的资产，再考虑防护机制。案例内容、用户身份、会话凭据、审批决定和模型密钥，不是同一种资产，也不应放在同一个位置。

| 资产或入口 | 可能的问题 | 本讲关注的边界 |
|---|---|---|
| 登录表单 | 猜口令、枚举账号 | 密码验证与可解释的失败 |
| 会话Cookie | 窃取、固定、重放 | 随机标识、轮换、过期、服务端销毁 |
| 案例修改接口 | 更换编号修改他人数据 | 对象级授权 |
| role/ownerId字段 | 客户端伪造身份或归属 | 服务端决定身份与可写字段 |
| 用户提交的标题 | 在页面中被解释为代码 | 按输出上下文转义 |
| 带Cookie的写请求 | 被其他站点诱导发出 | CSRF防护 |
| 后端配置 | 密钥进入前端或日志 | 服务端环境与最少公开信息 |

本讲实验只验证自己本机的课程服务和测试数据，不对外部账号或网站进行探测。使用随机端口的自动测试会自行准备独立账号，无需真实身份。

## 4. 把权限变成一张表

| 操作 | 匿名 | 普通用户 | 管理员 |
|---|---|---|---|
| 读取公开案例 | 允许 | 允许 | 允许 |
| 创建案例 | 登录检查失败 | 创建归自己的案例 | 创建归自己的案例 |
| 修改自己的案例 | 登录检查失败 | 允许 | 允许 |
| 修改他人的案例 | 登录检查失败 | 403 | 允许 |
| 查看一次运行 | 登录检查失败 | 仅本人运行 | 允许 |
| 批准练习工单 | 登录检查失败 | 403 | 还需检查请求状态 |

本表对登录检查的预期，均假设来源和CSRF已满足。公开案例与私有运行采用不同读取策略，不能机械地给所有GET加相同限制。

角色控制称为基于角色的访问控制（RBAC），owner关系表达对象归属。实际授权通常结合主体、资源、动作和状态，而不是只比较一个角色字符串。例如admin也不能把已拒绝运行重新当作待审批请求执行。

## 5. 三个可信位置

服务器确认的用户身份、服务器保存的资源归属、服务器执行的授权规则，共同决定是否允许操作。客户端可以提供目标编号与业务输入，但无权自行升级这些事实。

```text
req.session.userId → 服务端加载用户 → req.user
req.params.id     → 数据层加载资源 → item.ownerId
规则：本人或管理员 → 允许受限制字段更新
```

数据库外键维护引用是否有效，却不自动判断当前请求者是否有权访问。参数化查询阻止值改变SQL结构，也不能阻止一条语法完全合法的越权UPDATE。不同机制要解决不同问题。

## 6. 密码、Cookie、会话与Token的关系

密码用于证明用户知道某个秘密，不应在每个业务请求中反复发送。登录成功后，以会话或令牌代表后续访问资格。

Cookie是浏览器存储与自动携带数据的机制；服务端会话是服务器维护状态的一种设计；JWT是一种令牌格式。JWT也可以放进Cookie，Cookie也可以只携带随机会话编号。因此不能把“Cookie还是JWT”当作同一层面的二选一。

本课使用express-session：Cookie中主要是带签名的会话标识，用户id与CSRF值在服务端会话中。签名用于检测篡改，不等于加密；持有有效会话Cookie的人仍可能冒用该会话，不能随意分享。[express-session说明](https://expressjs.com/en/resources/middleware/session/)

## 7. 401、403与404如何使用

401表示当前请求没有可接受的认证身份；403表示请求被策略拒绝，可能是资源权限，也可能是来源或CSRF；404表示资源未找到，或按一致策略隐藏资源存在性。

本实验案例公开可读，因此修改他人存在的案例返回403，修改缺失编号返回404。私有资源可选择统一隐藏存在性的404策略，但应前后一致，且测试需要明确该选择。

错误码用于定位拒绝层，不能把所有403都显示为“密码不正确”。同时避免向客户端泄露密码散列、完整会话、连接字符串和内部堆栈。

## 8. 用失败证明边界

一条请求返回403，只说明某处拒绝了它。若想验证对象权限，先提供正确会话与CSRF，避免请求提前因另一层失败而使测试“假通过”。

验证alice不能修改bob案例时，记录bob原对象，发出带合法会话和令牌的PATCH，再读对象并比较。若403但标题已经变化，授权仍然有严重问题。

登录与退出也要验证服务端状态：登录后旧匿名会话不能变成已登录会话；退出后重放旧Cookie不能访问受保护接口。只在React中清空user不会使服务器会话失效。

## 9. 已实现机制与后续工作

现有course-lab包含密码散列验证、会话轮换、Cookie属性、同步CSRF令牌、来源检查、资源归属、服务端角色加载和退出销毁。默认内存会话适合单进程教学，PostgreSQL路线配置共享会话存储。

它尚未提供完整登录限流、MFA、密码找回、全部会话撤销、生产HTTPS及浏览器安全策略部署。统一登录失败消息也没有消除所有时序侧信道。学习时应识别这些边界，而不是把演示代码称为完整生产认证平台。

## 自检与参考答案

<details><summary>前端隐藏了编辑按钮，为什么还要检查ownerId？</summary><p>客户端可以绕过界面直接构造HTTP请求。授权必须在服务器根据已验证身份和目标资源执行。</p></details>

<details><summary>缺少CSRF的匿名POST得到403，是否说明未登录检查失效？</summary><p>不一定。本实验先检查CSRF，请求可能还没到登录检查。应取得匿名CSRF后再验证401。</p></details>

<details><summary>把会话用户的role保存到React state后，可以作为审批依据吗？</summary><p>只能用于界面提示。服务器仍需在每次请求中确认身份、角色、资源与状态。</p></details>

<details><summary>为什么安全测试要比较失败前后的数据？</summary><p>正确拒绝不仅要有状态码，还应没有未经授权的业务副作用。</p></details>
