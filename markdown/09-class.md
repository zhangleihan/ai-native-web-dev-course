# 实践练习：任务进度、断线恢复与取消

## 准备与目标

从课程根目录运行：

```bash
cd labs/realtime-basics
npm ci --ignore-scripts
npm run dev
```

打开 http://127.0.0.1:3009 ，同时准备浏览器Network。实验不需登录、数据库或模型密钥；数据为固定模拟步骤，服务重启清空。详细代码见[SSE与Express](#/part/9/d)和[React订阅](#/part/9/e)。

课堂核心约25分钟，先预测再操作，分别记录任务状态、连接状态和事件位置。不要只截一个最终绿色提示。

## 对照一：正常完成不只看HTTP200

选择“正常完成”，点击创建。检查POST只发生一次并返回201；events是一个持续的GET。页面收到#1开始、6次progress和#8完成，随后done使订阅关闭。

记录最终COMPLETED、6/6、序号8。若操作太慢才开始订阅，历史可能已淘汰；用新任务重做，不能把reset误判为服务损坏。

## 对照二：停止观察不等于取消

创建新任务后尽早点“停止订阅”，记下当时的seq和step。稍等后点“查询快照”，比较服务端是否继续前进，任务编号是否相同。超过约4.8秒后可能已经COMPLETED，这也说明任务未因停止订阅而取消。

查询只读取当前状态，不能补回全部日志。通过“查看服务诊断”核对subscribers归零；存在其他页面或控制台订阅时，它们仍会计入总数。

## 对照三：恢复同一个任务

停止订阅后点“重新订阅”，检查没有再次POST创建。若缺失事件仍在历史范围内，补发编号大于本页面已处理位置的事件；若已超出范围，显示reset提示与当前快照。

记录恢复前后任务id相同，已显示日志编号不重复。正常完成后反复重订阅不会重新执行任务。

## 对照四：明确取消

创建新任务，执行中点击“取消任务”。检查cancel接口返回的实际状态。若取消先被服务端处理，应为CANCELLED且进度不再增加；若任务已经完成，应保持COMPLETED。

使用控制台或自动验证再次取消同一任务，确认seq不再增加。注意：取消是业务操作；停止订阅、fetch.abort和关标签页不是它的替代品。

## 对照五：业务失败与连接错误

选择“第3步失败”并创建。预期先看到2次progress，再看到FAILED状态与done，任务停在3/6。HTTP流可以正常结束，但界面不能把FAILED显示成完成成功。

另开新任务，通过Network离线模式观察连接提示。恢复在线后再查询或订阅；实验结束关闭离线模拟。浏览器自动重连策略与Node测试分别记录，不把一类证据替代另一类。

## 对照六：主动制造历史缺口

等正常任务完成后点击“从头订阅”。本页面从位置0重新请求，但服务端只剩最近6条历史，因此发送reset+当前快照，再发送done。页面提示较早日志不可回放，业务仍为COMPLETED。

这是“恢复现在”而非“找回全部过去”。记录reset携带的seq与最终状态，解释为什么服务器不能伪造已经丢失的#1、#2。

## 不依赖手速的自动演示

在实验目录另开终端：

```bash
npm run demo
npm run check
```

demo使用随机本机端口与独立样本，自动验证6组对照，不连接或改变3009已有任务。check运行8项测试并构建React；包括跨字节中文解码、位置检查、资源清理和历史恢复。Node HTTP验证不代表所有浏览器、代理与生产部署均已验证。
