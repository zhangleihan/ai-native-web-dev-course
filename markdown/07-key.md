# 前后端集成：让请求、数据与界面保持一致

## 学习目标与课前准备

第四讲把页面拆成组件，第五讲建立API，第六讲让数据进入持久存储。本讲把这些部分接起来：页面读取服务端列表，用户提交表单，界面根据实际响应更新，并能在网络慢、接口失败和响应格式变化时保持可解释的行为。

学完后，应能封装基本请求、区分加载/成功/空结果/失败，管理React请求生命周期与竞态，完成一次可靠提交，使用同源代理或受限CORS联调，并提供能定位问题的请求证据。

先修为React state、props和Effect，HTTP/JSON与Promise/async/await，以及案例库的列表、创建和错误契约。实验使用Node20.18+，不需要数据库、账号或模型密钥；与第六讲持久化路线衔接时再替换存储。

## 1. 集成是一条完整的数据链

```text
用户动作 → 页面状态/表单草稿 → 参数与JSON请求
  → 浏览器/开发代理 → API校验与业务 → 数据存储
  → HTTP状态、响应头、JSON → 客户端解析与校验
  → 当前请求的结果进入state → 页面显示反馈
```

任何一层出错，都可能表现为“页面没有更新”。先找到断点，再修改对应层；不能看到空列表就立即重建数据库。

一次查询应能够说明请求条件、发送地址、HTTP结果、响应结构，以及界面为什么接受或忽略该结果。一次写入还要说明服务器是否已改变数据，客户端是否得到了确认。

## 2. 区分三类状态

| 状态 | 例子 | 保存在什么位置 |
|---|---|---|
| 本地交互状态 | 当前筛选、页码、表单草稿、是否展开 | 当前页面或组件 |
| 服务端业务状态 | 案例编号、规范化标题、总数、归属 | 服务端；按存储方案持久化 |
| 请求状态 | 正在读取、保存中、失败、结果未确认 | 客户端；描述一次通信过程 |

用户在表单里输入“  链路中断  ”，草稿可以暂时保留空格；保存成功后应采用服务器返回的标题和id，而不是自己拼一个假编号。页面数组是服务端结果的一个视图，不自动成为共享业务事实。

## 3. 一份契约先对齐四件事

| 内容 | 本讲独立实验约定 |
|---|---|
| 地址与方法 | GET /api/cases；POST /api/cases |
| 查询参数 | kw、industry、difficulty、offset、limit |
| 成功输出 | 列表含items/total/offset/limit；创建201含服务器生成id |
| 错误输出 | error含code/message/requestId；写入校验400 |

该契约来自第五讲express-basics，不等同于course-lab或FastAPI。FastAPI的校验错误422、detail结构与接口范围另有约定，不能只换端口就假设兼容。

第五讲[OpenAPI工具](#/part/5/g)可生成文档与类型。本讲继续检查真实JSON；生成TypeScript类型不能代替运行时校验。

## 4. 查询界面有四种可见结果

| 状态 | 页面反馈 | 不应出现的行为 |
|---|---|---|
| loading | 正在读取当前筛选，必要操作暂不可用 | 不标注来源地显示旧筛选结果 |
| success且非空 | 条目、总数与分页 | 把items.length当作全部匹配数 |
| success且为空 | 没有匹配案例 | 把合法空结果显示为系统损坏 |
| error | 错误类型、检查线索、重新读取入口 | 用空数组悄悄吞掉失败 |

本例在新查询开始时清空旧显示，便于理解。真实产品也可保留旧数据并标记“正在更新”，但要明确这些数据仍对应旧条件，避免误操作。

## 5. 查询与写入采用不同的触发方式

列表通常随筛选、页码或显式刷新同步，可放在Effect中。创建、修改、删除由明确的提交或点击触发，应放在事件处理函数中，而不是让“某个状态变了”间接触发写入。[React：哪些逻辑属于事件处理](https://react.dev/learn/you-might-not-need-an-effect)

组件渲染描述UI，不应直接发请求。请求返回后更新state会再次渲染；如果每次渲染都POST，就可能重复创建。开发环境的额外Effect检查也会暴露这种问题。

## 6. 慢的旧响应可能覆盖快的新响应

先查询“链路”，随后查询“订单”。第二个请求先返回时，页面应显示订单；第一个请求稍后返回，不应把页面改回链路。这类结果依赖异步完成次序的问题称为竞态。

可使用AbortController取消已失效的读取，并在更新state前检查它是否仍是当前请求。取消主要管理传输与资源，当前性检查维护界面正确性。搜索防抖减少请求数量，但不保证返回顺序，不能代替竞态保护。

本实验的LatestRequest同时使用取消与代次编号；即使某个异步任务没有响应abort，旧结果也不能发布。

## 7. 提交、确认与刷新分开处理

```text
本地草稿 → 前端即时校验 → 提交中
  ├─ 明确校验拒绝 → 保留草稿，显示错误
  ├─ 返回201 → 使用服务器对象，显示已创建 → 独立刷新列表
  └─ 网络/代理等异常 → 结果未确认 → 查询核对后再决定下一步
```

创建已获201确认后，后续列表刷新失败，不应把“创建成功”改成“保存失败”。新对象不满足当前筛选时，也可能暂时不显示在列表中；总数、排序和分页应由服务器查询决定，不能盲目把条目插到任何列表顶部。

本例采用先等待服务端确认再更新的保守方式。乐观更新会先改变界面，随后在失败时回滚，需要更明确的冲突处理，不作为本讲默认实现。

## 8. 失败不总能证明没有副作用

空标题被服务器明确拒绝，与响应在返回途中丢失，是不同情况。即使客户端等待超时，服务器也可能已经完成写入。AbortController中止fetch不等于数据库事务回滚。

本讲提供“已写入但响应中断”场景，代理会返回502。页面保留草稿并提示先核对列表，不自动再次POST。真正需要安全重试创建操作时，还要设计服务器端幂等机制；禁用按钮只能减少本页面重复操作，不能解决所有重复请求。

## 9. 明确浏览器实际访问哪个服务

| 地址 | 用途 |
|---|---|
| 127.0.0.1:8766 | 静态教材；不负责业务API |
| 127.0.0.1:3031 | 本讲React页面与/api开发代理 |
| 127.0.0.1:3030 | 本讲实际Express API |

浏览器用相对/api时，先请求3031，由代理转发3030；这对浏览器是同源请求。直接请求3030则是跨源，需要对应CORS读取许可。不要把教材端口、前端服务与API服务混成同一个入口。

## 10. 接入Next.js或已有项目

Next.js可以由服务端页面读取初始数据，也可由客户端组件处理交互；要先确认代码运行位置。浏览器中的fetch受浏览器跨源规则限制，服务器之间的请求不以同一方式受CORS约束，但仍需要正确的身份与授权。

第4讲现有Next.js实验的/remote演示只读调用，/cases包含本地数据。不能把本地新增当作后端已经持久保存；本讲先打通一条真实链路，再扩展框架的数据获取方式。

## 自检与参考答案

<details><summary>加载失败时返回空数组，界面不报错，是更友好吗？</summary><p>不是。用户会把服务失败误解成没有数据。应把合法空结果与错误分别显示。</p></details>

<details><summary>搜索加了300毫秒防抖，还需要处理旧响应吗？</summary><p>需要。不同查询仍可能先后重叠，返回顺序与发送顺序不同。防抖优化请求频率，不保证当前性。</p></details>

<details><summary>POST超时后可以直接自动重发吗？</summary><p>不能仅据超时判断未写入。应确认业务结果，或在服务器支持幂等策略后按契约重试。</p></details>

<details><summary>保存成功，但当前筛选列表看不到新对象，是否一定是后端没写入？</summary><p>不是。可能不匹配筛选、位于其他页或刷新失败。用返回的id和独立查询核对。</p></details>
