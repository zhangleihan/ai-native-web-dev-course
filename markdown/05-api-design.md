# 接口设计与调试：把“可以调用”变成明确契约

## 1. 从页面行为提取资源

案例库有列表、详情、新建和编辑四类界面。先列出每种界面需要的数据与操作，再确定请求；不能把每个按钮都机械变成一个不相关接口。

| 页面操作 | 需要的数据或动作 | 请求职责 |
|---|---|---|
| 打开列表 | 条目、匹配总数、当前页 | 查询案例集合 |
| 选择行业 | 根据行业重新读取 | 在集合查询中传筛选条件 |
| 打开详情 | 指定案例完整表示 | 按编号查询 |
| 保存新建表单 | 服务器生成编号并写入 | 创建资源 |
| 修改标题 | 改变可写字段 | 局部更新 |
| 确认删除 | 移除目标资源 | 删除资源 |

本课实例使用一个案例集合支撑这些页面。列表卡片上的统计数量通常来自查询结果，不必再增加一个“统计接口”；当统计需要复杂聚合、权限或缓存时，再单独设计。

接口的完成标准包括路径、方法、输入、成功响应、失败响应和副作用。仅记录“POST 新增案例”无法指导前后端协作。

## 2. 为创建接口写一份可检查的说明

**接口：** POST `/api/cases`。本节描述 `labs/express-basics` 的实际契约，默认端口3002；Python 对照端口为8001，错误格式不同。

| 字段 | 输入规则 | 处理方式 |
|---|---|---|
| title | 字符串，去首尾空白后1–100字符 | 保存规范化后的标题 |
| industry | 字符串，去首尾空白后1–50字符 | 保存规范化后的行业 |
| difficulty | beginner/intermediate/advanced | 保存枚举值 |
| id | 不允许提交 | 服务端生成 |
| 未声明字段 | 不允许提交 | 400，避免误写或夹带字段 |

边界长度在本例中按 JavaScript 字符串 length 计算，不能简单理解为所有人类语言中的字数；若产品对 emoji 等字符有精确计数要求，需要统一前后端的计数规则。

成功为201；Location 指向新对象；错误为统一 error 对象。请求失败前不修改集合。网络超时则无法仅凭客户端判断“写入未发生”：服务器可能已经完成创建但响应未送达。自动重试创建请求需要幂等键等额外机制，本实验未实现。

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "title 必须是1至100个字符的非空字符串",
    "requestId": "服务端生成的请求编号"
  }
}
```

code 供程序分类，message 帮助人理解，requestId 对应日志。若前端直接根据完整中文消息判断业务类型，文字调整就可能破坏逻辑，应优先使用稳定的 code。

## 3. 状态码与错误分层

| 层次 | 例子 | 本实验响应 | 首先检查 |
|---|---|---|---|
| 网络连接 | 没有服务监听 | 没有 HTTP 响应 | 启动日志、主机、端口 |
| 路由 | `/api/case` 拼错 | 404 | 方法和路径 |
| 内容类型 | POST 发送 text/plain | 415 | Content-Type |
| 语法解析 | JSON 少一个引号 | 400，INVALID_JSON | 原始请求体 |
| 体积限制 | JSON 大于32KB | 413 | 上传内容及限制 |
| 字段校验 | 空标题、错误枚举 | 400，VALIDATION_ERROR | 字段、类型和范围 |
| 资源查询 | 编号未找到 | 404，NOT_FOUND | 编号与数据状态 |
| 未预期异常 | 存储方法抛错 | 500，INTERNAL_ERROR | 请求编号与服务日志 |

第8讲还将讨论401身份未确认和403权限不足；409可用于业务冲突。无需为了记住状态码而在本讲人为实现所有错误。不同框架可以选择不同校验状态码，但一个应用内部应有明确约定。

200但 items 为空是成功查询的空结果；500是执行失败。若前端把两者都显示为“没有案例”，使用者将无法判断是否需要重试。

## 4. 把查询参数设计清楚

Express 参考实验支持 `kw`、`industry`、`difficulty`、`offset`、`limit`。多个条件按交集计算。例如 `kw=链路&industry=通信` 要同时满足关键词与行业，而不是满足任意一项。

```json
{
  "items": [{"id":"示例编号","title":"链路中断","industry":"通信","difficulty":"beginner"}],
  "total": 2,
  "offset": 0,
  "limit": 1
}
```

此处是响应形状示意：匹配两条，本页最多返回一条。offset 默认为0，limit 默认为10，范围1–50。total 是筛选后、分页前的数量，不是数据库全部案例数，也不是当前页条目数。

参数校验必须处理不合法整数、重复键和超大范围。未知的列表查询键在本实验中被忽略，而重复的已知键可能形成数组并被拒绝。创建请求体的未知字段则会被拒绝；二者的严格程度应在契约中分别说明。

中文关键词可以让客户端正确编码：

```bash
curl -i --get http://127.0.0.1:3002/api/cases \
  --data-urlencode 'kw=链路' --data-urlencode 'industry=通信' \
  --data-urlencode 'offset=0' --data-urlencode 'limit=1'
```

在数据量较大时，还需稳定排序与索引；即便 limit 较小，先遍历全部数据仍可能昂贵。本讲内存算法用于理解契约，第6讲再将筛选与分页映射到 SQL。

## 5. PUT 与 PATCH：完整替换和部分修改

假设对象原值为“链路中断、通信、beginner”。只提交 `{"title":"链路恢复"}`：PATCH 可约定保留其他字段；PUT 的完整替换契约通常要求提交全部可写字段，不能随意当作 PATCH 使用。本实验只实现 PATCH。

字段未出现与显式 null 也是两种意图。本契约不允许把 title 清空，因此 `{"title":null}` 返回400；空对象也返回400。若未来增加可以清空的描述字段，就需要分别定义“省略表示不变、null表示清除”的规则。

```bash
# 先把实际创建的编号填入变量
case_id='把创建响应中的id填在这里'
curl -i -X PATCH "http://127.0.0.1:3002/api/cases/$case_id" \
  -H 'Content-Type: application/json' -d '{"title":"链路恢复"}'
```

以上是字段合并式 PATCH，语义由本应用定义；它不是 `application/json-patch+json` 的操作序列格式。采用特定补丁标准时，需另外遵循对应格式与内容类型。[PATCH 的语义与约束](https://www.rfc-editor.org/rfc/rfc5789.html)

两个用户同时编辑时，后保存的请求可能覆盖先前结果。版本号、ETag/If-Match 和事务可以参与并发控制，本实验没有实现这些机制，不把“页面能保存”视为已解决并发更新。

## 6. 用工具检查请求与响应

### 6.1 curl：先脱离页面定位

```bash
curl -i http://127.0.0.1:3002/api/health
curl -i -X POST http://127.0.0.1:3002/api/cases \
  -H 'Content-Type: application/json' \
  -d '{"title":"链路中断","industry":"通信","difficulty":"beginner"}'
```

`-i` 展示状态行与响应头，`-H` 设置请求头，`-d` 提供请求体。创建后复制 Location，GET 同一路径，比较响应对象。如果只测试健康接口，尚未验证任何案例数据读写。

默认浏览器地址栏不能替代这些写入请求。Postman、VS Code REST Client 等也可以保存请求，但工具名称不影响 API 语义。配套实验的 `requests.http` 可作为手工调用记录。

### 6.2 浏览器 Network：核对真实调用

在已接入接口的页面打开开发者工具，保留网络日志，再执行一次操作。依次检查 Request URL、方法、Request Headers、Payload、状态码和 Response。若请求发到了8766教材端口，修改 Express 路由不会解决问题。

单独用浏览器 Console 调用不同端口可能遇到跨源限制。先用 curl 确认后端行为，再在第7讲处理 CORS 或代理。curl 不执行浏览器的 CORS 限制，因此“curl 成功、浏览器失败”是有用的定位线索。

### 6.3 自动测试：保存可重复证据

Express 实验使用 Node test runner 与 fetch，在随机端口启动应用；FastAPI 实验使用 TestClient 直接调用应用。测试既比较状态码，也检查对象内容和失败后的集合状态。

测试应能发现真实错误，例如“空标题请求返回400但仍插入数据”“分页前忘记筛选”“更新时覆盖未提交字段”。重复断言函数内部实现细节，对接口维护帮助较少。

## 7. 看到错误后按层排查

| 现象 | 一次决定性的检查 | 下一步 |
|---|---|---|
| Connection refused | curl 健康接口也失败 | 检查进程和端口是否一致 |
| EADDRINUSE | 启动日志提示端口占用 | 选空闲端口，别结束无关服务 |
| Cannot GET 或404 | 检查实际请求的方法和路径 | 核对前缀、单复数与路由挂载 |
| req.body 为 undefined | 查看 Content-Type 和中间件顺序 | 在路由前解析 JSON，修正发送方式 |
| 一直等待 | 跟踪最后一条日志 | 查找既未响应也未 next 的分支 |
| Headers already sent | 检查同一分支是否响应两次 | 返回后结束函数，修正异步分支 |
| 中文输入异常 | 比较原始 JSON 与 URL 编码 | 使用 JSON UTF-8 与正确参数编码 |
| 数据突然清空 | 检查开发热重载日志 | 确认进程是否重启，记录内存边界 |
| 500 | 找响应的 X-Request-Id | 对应日志并复现存储失败 |

每次保留一条最小失败请求，再只修改一个可能原因。改变数据库、框架版本与前端代理后一起重试，会失去判断依据。

## 8. 契约怎样服务于前后端协作

开发前共享一份接口表、字段表和成功/错误样例；实现后用请求验证它们。前端可以先用契约生成模拟数据，后端也能独立运行。切换真实接口时，不把不同错误结构悄悄当成同一种响应。

FastAPI可以从路由与模型生成OpenAPI描述；Express框架本身不会自动生成。本讲新增[OpenAPI与自动化工具](#/part/5/g)，为Express案例独立维护描述，运行规范检查、交互文档、前端类型生成和真实响应验证。无论描述来自代码还是手工编写，都要检查错误与边界；文档和实现可能同时遗漏同一业务规则，仍需业务测试与人工审阅。

## 自检与练习

<details><summary>为什么不能把所有错误都返回200，再写一个 success:false？</summary><p>HTTP 客户端、监控与缓存等会依据状态码判断结果。统一返回200削弱了这种语义，前端也更容易把失败当成功。</p></details>

<details><summary>PATCH后的标题正确，就能证明更新接口正确吗？</summary><p>还需检查其他字段是否保留、编号是否稳定、非法输入是否被拒绝、缺失资源是否为404，以及失败时是否未修改原记录。</p></details>

<details><summary>为什么自动文档不能代替业务测试？</summary><p>文档描述输入输出结构，不能自动证明用户有权限、状态转换被允许或失败没有副作用。</p></details>

练习：为自己的期末项目选择一个资源，写出集合、详情、创建、修改、删除的契约；给出正常、缺失、校验失败三种请求。标明已实现与尚未实现的接口。
