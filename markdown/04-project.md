# 项目关联：让案例库拥有清晰的组件边界

## 从独立练习过渡到贯穿项目

本讲使用 [React 基础实验](labs/react-basics/README.md) 理解组件与状态。后续 [全栈实验](labs/course-lab/README.md) 再加入 API、认证和 AI 能力。先在本地静态数据上验证界面规则，才能在请求出错时区分“界面逻辑问题”与“服务端问题”。

| 组件/数据 | 本讲职责 | 后续接入服务时的变化 |
|---|---|---|
| CasesPage | 拥有筛选条件、收藏 id，计算可见列表 | 读取案例接口结果；加入请求状态 |
| FilterBar | 展示筛选值，调用父组件回调 | 大数据时可把条件变为查询参数 |
| CaseList | 展示列表与空态 | 区分加载中、请求失败和真实空结果 |
| CaseCard | 展示单条案例，报告收藏意图 | 保持展示与交互接口清晰 |
| initialCases | 只读练习数据 | 替换为接口返回数据，不伪装成已入库 |
| favoriteIds | 当前页面内存中的用户选择 | 需要跨刷新保留时再设计存储与账号归属 |

不要因为后续会接 API，就在本讲给每个组件预先增加 Effect、网络请求或一套全局状态库。组件接口应能解释具体需求：例如 `onToggleFavorite(id)` 表示用户要切换哪条案例，而不是把整个 DOM 事件一路传到数据库层。

## 设计检查

画一棵自己项目的组件树，在树旁标记每份 state 的拥有者。对每个字段追问：它是否由父组件提供？是否能由其他字段计算？哪些组件需要读或修改它？只有最后仍需记忆的事实才进入 state。

最小交付：一个可复用的卡片、一个受控筛选区、一个使用稳定 key 的列表、一处明确的共享状态拥有者、一个空结果界面。展示一次“用户操作 → 回调 → setter → 新 props”的完整链路。

保留示例对刷新后丢失收藏的说明；这是真实的持久化边界。后续接入 AI 诊断时，诊断输入、加载状态、结果与错误也应分别说明拥有者及生命周期，而不是让多个组件各存一份相互矛盾的数据。
