# 项目关联：为一个业务资源建立持久化边界

## 本讲在主线中的位置

第五讲定义接口契约，本讲把案例存储从内存改为关系数据库，第七讲继续连接前端。先贯通一个资源，确保校验、存储与响应一致，再扩展认证和复杂业务关系。

| 当前能力 | 本讲增加的机制 | 可验证结果 |
|---|---|---|
| Node内存集合 | 文件型引擎或PostgreSQL | 服务重启后记录可读 |
| API字段校验 | 数据库约束 | 直接写SQL也拒绝非法值 |
| 多处重复作者属性 | 作者表与外键 | 修改作者只需维护一处 |
| 字符串标签列表 | 标签与关联表 | 关系可查询且不能重复 |
| 多条独立写入 | 单一事务边界 | 后续失败不留下前半结果 |

## 代码阅读路线

先读labs/database-basics的schema、repository和database适配器，再比较综合labs/course-lab中的PgStore及001_initial.sql。综合模型包含users、owner_id、运行、审批和工单；入门模型使用authors演示关系，未实现登录，两套表不能混用。

FDE UI副本目前仍是前端模拟。接入时先确定一个资源的数据库结构和API，再替换对应模拟数据入口；不能通过复制四张教学表就声称访谈、审批、运行轨迹都已持久化。

## 最小完成范围

为期末项目选择一个资源，给出字段和约束，实现集合、详情与创建落库。保持第五讲契约，记录一次成功创建、一次非法写入和一次服务重启后的读取。

## 选修拓展

需要用户归属时先画关系再加外键；需要多步写入时给出事务边界；需要优化时保存查询、计划与测量条件。数据库迁移、API表示和UI状态分别记录，避免将三者混成一层。
