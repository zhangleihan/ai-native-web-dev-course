# AI 氛围编程：系统 UI 原型设计

## 学习目标与课前准备

本节综合运用 React、Next.js 和 Ant Design，学习如何通过自然语言描述需求，与 AI 逐步完成系统界面。完成后，应能说明页面如何围绕业务任务组织、组件和状态如何协作，以及生成结果怎样验证。

氛围编程（Vibe Coding）可以帮助快速形成原型，但运行和理解仍是学习过程的一部分。生成页面后，需要阅读关键代码，解释状态变化，检查成功、失败与取消操作，不能只凭外观接受结果。

先完成 [React 状态设计](#/part/4/d)、[Next.js](#/part/4/e) 和 [Ant Design](#/part/4/f)，再进入 [FDE 工作台完整案例](#/part/4/h)。FDE 原型采用自己的既有技术版本，不需要把它升级到入门实验的版本。

## 1. 从页面生成转向系统设计

系统 UI 原型要回答：谁在使用、当前要完成什么任务、操作后数据怎样变化、遇到问题如何恢复。FDE 工作台的任务主线是：案例进入、业务发现、问题定义、方案设计、受控运行和成果评测。

```text
业务情境 → 页面与路由 → 统一外壳和视觉规范
→ 最小可操作流程 → 跨页面状态 → 异常反馈 → 验证与修正
```

不要一开始就让 AI 一次生成所有页面。先完成一个可操作的业务过程，再扩展相邻模块，容易发现遗漏的数据和交互规则。

## 2. 准备需求情境包

情境包不是新的编程语言，而是一份提供给 AI 的项目背景。可将其保存为 `docs/ui-brief.md`，与现有 package.json、关键组件和设计资料一起提供。

| 内容 | FDE 示例 |
|---|---|
| 用户与目标 | 项目成员完成从业务发现到 AI 方案交付的实训 |
| 核心任务 | 查看案例、开展访谈、确认洞察、设计方案、检查运行与审批 |
| 页面关系 | 全局工作台 → 项目工作区 → 阶段页面 |
| 数据约定 | 项目、访谈、洞察、运行片段和审批记录 |
| 实现条件 | 复用现有 Next.js、TypeScript、Ant Design 与 React Flow |
| 视觉规范 | 分组导航、统一标题与主操作、固定状态颜色、可读的密集信息 |
| 边界 | 使用前端模拟数据，不声称已经实现模型服务、部署或后端权限 |
| 完成标准 | 导航正确，同一项目与运行状态在多个页面中一致，操作结果可解释 |

只提供相关文件，避免把真实账号、密钥或无关目录加入上下文。已有工程应先读取依赖和目录，不能照搬另一项目的 API 用法。

## 3. 分轮协作

| 轮次 | 给 AI 的任务 | 本轮需要检查的成果 |
|---|---|---|
| 需求分析 | 把产品文档整理为用户任务、页面与状态 | 每个页面有明确用途 |
| 页面骨架 | 建立 AppShell、路由和占位内容 | 跳转正确，导航位置明确 |
| 视觉规范 | 集中设置主题、间距、字体与状态颜色 | 不同页面具有一致层级 |
| 业务交互 | 实现一个案例或访谈流程 | 操作确实改变目标数据 |
| 共享状态 | 统一项目、角色、运行等上下文 | 跨页面数据一致 |
| 迭代修正 | 根据具体问题完善布局和反馈 | 修改可以复现和验证 |

第一轮提示可以这样写：

```text
请先阅读设计文档、package.json 和现有目录，不修改代码。
按用户任务列出页面、主要信息、操作与结果，说明状态放在哪里。
区分现有功能、模拟交互和待实现的后台能力。
把实现拆成若干可以独立运行和检查的小步骤，不新增无关依赖。
```

完整案例提供各轮可复用提示词。它们是根据 FDE 当前设计与代码重建的复现模板，不是未经核实的历史对话。

## 4. 用组件和状态连接页面

React 组件描述局部界面；Next.js 路由组织页面；Ant Design 提供表格、表单、布局与反馈控件。复杂关系图可通过独立画布组件封装，避免每个页面重复实现。

把项目、角色、运行过程等跨页面数据交给共享状态，把搜索词、弹窗和未提交草稿保留在页面或表单内部。能由已有数据计算的数量和筛选结果，通常不需要再维护一份状态。

FDE 中 `StoreProvider` 管理共享数据，`AppShell` 读取当前项目并组织导航。需要特别区分：方案设计页的局部编辑、跨页共享的运行状态，以及刷新后恢复初始值的模拟数据。这些行为并不等价于数据库持久化。

## 5. 给出可执行的修改反馈

反馈需要包含页面、操作、实际表现、期望行为和修改范围。

```text
问题位置：业务发现页的三栏布局。
复现：缩窄浏览器后，对话输入框和右侧洞察操作难以同时看到。
期望：保持主要操作可见，宽度不足时调整区域排列；表格局部滚动。
范围：只改布局与可访问性，不改访谈脚本和状态结构。
请报告修改文件、检查结果和仍未解决的问题。
```

“专业一些”可以进一步拆成：统一标题与按钮层级、明确当前任务、减少无关装饰、显示等待原因、提供取消与恢复入口。视觉风格必须服务于信息和操作，而不只是改变配色。

## 6. 检查原型是否真正可用

先检查一条完整流程，再检查异常情况：导航是否正确？编辑是否只在保存后生效？页面之间的数据是否一致？空结果与失败是否区分？角色切换是否仅为演示？刷新或切换项目会重置哪些状态？

构建通过只说明工程能够生成运行文件；真实交互需要在浏览器中操作。将实际结果记录到检查表，未运行的项目保留“未验证”，不要把 AI 的完成说明当成测试证据。

## 第二次平时作业：应用界面设计

围绕期末项目，使用 React、Next.js 和 Ant Design 实现首页、业务列表、详情及新增编辑界面，支持搜索筛选、分页、表单校验、删除确认和操作反馈。合理拆分组件，使用共享布局与动态路由，保持跨页面数据一致。界面简洁、中文规范，兼顾窄屏。提供不少于10条模拟数据，暂不要求真实后端或 AI 接口。提交源码、运行与设计说明、3分钟演示，注明 AI 辅助使用情况。评分：功能40%、技术30%、界面20%、文档与演示10%。成果作为期末大作业的 UI 基础。

## 自检与参考答案

<details><summary>为什么先整理情境包，而不是直接生成所有页面？</summary><p>情境包明确用户、任务、数据、工程约束与检查标准，使实现能够对照验证，减少 AI 猜测业务造成的返工。</p></details>

<details><summary>多个页面显示了同一项目名称，就代表共享状态正确吗？</summary><p>不代表。还需改变项目或运行状态，检查导航、详情和相关页面是否同步，以及重置行为是否符合约定。</p></details>

<details><summary>可以把模拟审批按钮当作权限系统吗？</summary><p>不能。它只展示交互与状态变化；真实权限必须由服务端验证身份与操作范围。</p></details>
