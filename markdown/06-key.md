# 数据库与数据建模：从内存对象到关系数据

## 1. 数据库解决哪些问题

浏览器状态保存当前界面的数据，后端数组保存当前进程的数据；数据库管理可长期保存、可检索并可由多个应用访问的数据。持久化只是其中一项能力，约束、事务和查询同样重要。

| 场景 | 内存数组的局限 | 数据库提供的机制 |
|---|---|---|
| 服务重启 | 数据丢失 | 持久化存储 |
| 查找某行业案例 | 遍历和筛选整个数组 | 查询语言与可用索引 |
| 两个写入入口 | 规则可能各写各的 | 统一约束 |
| 创建案例并关联标签 | 第二步失败可能留半条结果 | 事务 |
| 多人修改 | 读写竞争难以约束 | 事务隔离与并发控制 |
| 字段逐渐增加 | 手工改库难以追踪 | 版本化迁移 |

数据库不能替应用决定“谁可以修改案例”。它能执行权限配置和约束，但业务所有权、认证、授权仍需结合应用设计。第8讲再将已验证的用户身份关联到记录。

## 2. 认识数据库的层次

数据库管理系统（DBMS）是管理数据的软件，PostgreSQL是一种DBMS；数据库是其中一个独立的数据空间；模式（schema）对表等对象分组；表包含行和列。

```text
PostgreSQL服务
  → 独立练习数据库
    → 模式，如public
      → 表：cases、authors、tags、case_tags
        → 行：某条具体记录
        → 列：id、title、difficulty等属性
```

SQL是操作关系数据的语言，pg或psycopg是应用连接数据库的驱动，ORM在对象和表之间提供映射。它们处于不同层次，不是互相替代的数据库名称。

关系表强调记录、属性及其规则，而不是电子表格的单元格位置。没有ORDER BY，查询结果没有稳定顺序；“第一次恰好按插入顺序返回”不构成接口保证。

## 3. 先确定业务事实，再画关系

围绕案例库，先提出四个问题：哪些事物需要独立标识？每类事物有什么属性？它们之间有什么关系？哪些状态不能出现？

| 业务事实 | 模型决策 |
|---|---|
| 一条案例长期独立存在 | cases使用稳定id |
| 一个作者可以维护多条案例 | cases通过author_id关联authors |
| 案例可以暂未指定作者 | author_id允许NULL |
| 一条案例有多个标签，同一标签也用于多条案例 | 通过case_tags关联两端 |
| 同一个案例不能重复关联同一标签 | case_tags使用联合主键 |

本实验的authors只表示教学中的作者资料，没有登录凭据和认证能力。它与综合course-lab中的users/owner_id模型不是同一份表结构，不应混用迁移文件。

```text
authors 1 ───────< cases 1 ───────< case_tags >─────── 1 tags
                     author_id         case_id、tag_id
```

这是一对多与多对多关系。每条关联记录指向一条案例和一个标签；集合关系通过多条记录表达，不把“网络,排障”塞进一个字符串字段后再手动拆分。

建模时还要考虑可选性。一条案例至多关联一位作者，因此外键位于cases；允许未指定时为NULL，要求必有作者时再增加NOT NULL。不要仅根据页面上有几个下拉框来确定表数量。

## 4. 主键、候选标识与外键

主键唯一识别一行，并且不能为空。本课用UUID，避免把标题当作身份；标题可以修改，也可能重复。UUID与自增整数都有适用场景，类型不是唯一性规则本身，仍需PRIMARY KEY或UNIQUE。

作者username在本实验中要求唯一，属于额外的业务唯一约束。现实中“显示姓名”常会重名，不能未经分析就设为唯一。唯一规则必须来自业务含义。

外键确保引用指向存在的记录。例如author_id不能指向不存在的作者，但可以指向同一作者的多条案例。外键不会自动把作者姓名复制进案例；需要关联查询时再读取。

| 约束 | 含义 | 本课示例 |
|---|---|---|
| PRIMARY KEY | 标识唯一且非空 | cases.id |
| NOT NULL | 必须存在值 | cases.title |
| UNIQUE | 指定值或组合不得重复 | authors.username |
| CHECK | 对行内值执行条件约束 | difficulty枚举 |
| FOREIGN KEY | 引用必须有效 | cases.author_id |

CHECK通常不会因为表达式结果为NULL而拒绝该行。因此“非空且符合枚举”需要NOT NULL与CHECK配合，不能只写CHECK。[PostgreSQL约束](https://www.postgresql.org/docs/16/ddl-constraints.html)

## 5. 分表与规范化的直观理由

假设每行案例都重复保存author_name和author_email，作者改邮箱时就要修改多行；漏改一行会产生矛盾。把作者独立成表，以author_id引用，可以让作者属性只维护一份。

同样，把多个标签放进tag1/tag2/tag3列会限制标签数量；使用逗号字符串又使唯一性和关联查询困难。标签表与中间表可以明确表达关系，并用联合主键防止重复关联。

入门阶段可用三个问题检查设计：一列是否表达清楚的值？非主键属性是否描述当前实体？是否存在应独立维护却重复出现的信息？这有助于理解规范化，不能代替完整的函数依赖分析。

并非所有重复信息都必须立即消除。行业目前只是少量文本，等出现独立行业编码、名称变更与管理需求时，再考虑industry表。为了报表性能保留冗余也可以成立，但应说明更新规则和测量依据。

## 6. 选择类型与处理NULL

| 类型 | 本课用途 | 需要注意 |
|---|---|---|
| UUID | 主键与对应外键 | 类型一致，API仍接收文本表示 |
| TEXT | 标题、行业、标签名 | 类型不限制业务长度，需额外校验 |
| INTEGER | 整数数量、计数 | 不表示可含小数的金额 |
| NUMERIC | 需要精确小数的值 | 精度与小数位依据业务确定 |
| BOOLEAN | 是/否标志 | 区分false与NULL |
| TIMESTAMPTZ | 创建等时间点 | 展示随时区设置转换，不保留原时区名称 |
| JSONB | 结构变化的附加数据 | 不宜无分析地替代全部关系字段 |

NULL表示未知、缺失或不适用，由契约确定具体含义。空字符串、0、false是已知值，不能与NULL混为一谈。查询缺失作者写 `author_id IS NULL`，不是 `author_id = NULL`。

若应用把日期格式、字段命名或数据库类型直接原样暴露，前端可能依赖内部细节。接口表示与数据库结构可以分别设计，再在数据访问层转换。

## 7. 三个位置的校验各有用途

前端校验提供即时反馈；API校验处理不可信请求并给出可读错误；数据库约束防止其他写入路径和代码缺陷破坏共同规则。

例如非法difficulty应在API入口被拒绝；绕过API直接写SQL时，CHECK仍会拒绝。数据库拒绝不代表API可以不校验，否则用户很难获得清楚的字段提示。

外键删除策略也需要明确。本实验删除作者采用RESTRICT，避免案例引用失效；删除案例时其中间表关联使用CASCADE，因为该关联没有独立存在的意义。这不意味着可以级联删除真实审计历史。

## 8. 从单表进入完整应用

最小案例表可以先只有id、title、industry、difficulty、created_at，之后按需要加入作者、标签与关联。配套数据库实验为了展示关系，一次提供了这四张教学表，但核心API只读写案例的可公开字段。

数据库返回值不必全部发送给客户端。接口继续返回id、title、industry、difficulty；author_id等内部关联按后续需求另行公开。连接字符串由服务端读取，不放进React代码或提交到仓库。

本讲实验默认文件型PGlite，关闭再打开同一数据目录可保留记录；同时设置LAB_STORAGE=postgres和DATABASE_URL后切换到PostgreSQL服务。两条路线共享主要SQL与数据访问代码，运行环境、连接池与并发行为需要分别验证。

<details><summary>为什么不用标题作为案例主键？</summary><p>标题可能重复和修改，不适合作为长期身份。稳定id标识资源，标题表达当前业务属性。</p></details>

<details><summary>有外键就一定能防止作者重复维护同一标签吗？</summary><p>外键只保证引用有效。防止同一案例重复关联同一标签，需要对case_id、tag_id组合设置主键或唯一约束。</p></details>

<details><summary>为什么CHECK不一定能替代NOT NULL？</summary><p>CHECK对NULL结果的处理不等于“必须有值”。必填字段应同时声明NOT NULL与值约束。</p></details>

<details><summary>把作者姓名分到另一张表，是为了多写一条JOIN吗？</summary><p>主要是明确实体与减少重复维护，避免作者属性更新后多条案例不一致；JOIN是重新组合信息的查询方式。</p></details>

<details><summary>文件型PGlite重启后保留数据，证明了什么？</summary><p>证明本实验数据在所用文件型引擎中的持久化；没有证明PostgreSQL TCP连接、连接池、多连接并发或生产备份都正常。</p></details>
